# 桌面 Markdown 交付验收

这个最小闭环由 Hearth OS 生成内容，受限交付步骤将已发布产物原样保存到指定桌面文件，Hearth Eval 的检查器再独立读取文件验收。执行器的“已完成”回复不作为通过依据；交付步骤不生成或修改内容。

## 启动

先启动同一台电脑上的 Hearth OS（默认 `127.0.0.1:4317`），并在 Hearth 中配置可用的 native 聊天模型。此入口使用普通任务 API，不要求开启 `HEARTH_EVAL_MODE`。

```powershell
cd E:\codex-eval-agent\hearth-os
npm ci
node --import tsx apps/server/src/index.ts
```

如需处理 Hearth 审批，可另开终端启动其前端：

```powershell
cd E:\codex-eval-agent\hearth-os
npm run dev -w @hearth/web -- --port 5173 --strictPort
```

按[启动评测台](./local-start.md)启动或重启 Eval 的前后端，打开 `http://127.0.0.1:5175/acceptance`，也可以从侧栏进入“交付验收”。旧后端必须重启才能提供新接口。

## 使用

1. 确认页面显示的桌面目录。Windows 使用系统桌面目录，支持系统配置的桌面重定向；其他平台默认使用 `~/Desktop`。必要时通过 `HEARTH_EVAL_DESKTOP_DIR` 指定已有目录并重启 Eval。
2. 填写一个尚不存在的 `.md` 文件名、一级标题和必含文本（每行一项）。
3. 选择是否允许验收失败后自动修复一次，再点击“开始执行与验收”。这会调用 Hearth 模型并产生实际文件。
4. 如显示等待审批或补充信息，按页面记录的任务 ID 到 Hearth 处理。Eval 不代替用户批准。
5. 查看每轮验收结果、反馈、文件大小、SHA-256 与检查时间。

## 执行与判断

```text
冻结文件路径与内容要求
  → POST Hearth /api/tasks 创建 native 任务
  → GET Hearth /api/tasks/:id 等待结束
  → 下载当前运行的指定发布产物，核对大小和 SHA-256
  → 受限交付步骤原样保存到指定桌面文件
  → Eval 直接读取桌面文件
  → 通过：保存证据并结束
  → 未通过且授权修复：把失败项交给新的 Hearth 任务
  → 再次读取真实文件，保存新的证据并给出最终结果
```

检查项为：路径正确、普通文件、有效 UTF-8、非空文本、首个非空行为指定一级标题、正文包含全部必含文本。不会因最终回复声称完成而通过。检查失败和修复反馈都保留，验收条件不在修复时改写。

Hearth 在任务沙箱内生成声明的期望产物；可用工具为 `read_file`、`write_file`、`edit_file`、`ask_user`、`finish_task`，不授予 shell 或网络工具。交付适配器只保存到冻结的单一桌面路径，不接受模型返回的任意目标路径。已有同名文件拒绝开始；修复仅替换上一轮已记录哈希且未被外部修改的文件。链接、目录和无法确认安全的路径停止交付。文件上限为 256 KB。

基础文件检查由确定性程序执行；Hearth 的模型负责实际执行和依据失败证据修复。启用下文的共享记忆模式后，还会调用独立模型评委进行语义评审。本版不是通用自主诊断 Agent。

## 中断与证据

- 每轮最多等待 10 分钟，包括审批时间。超时尝试取消任务，失败会明确显示。
- “停止并取消执行”不会删除已写出的文件；外部取消是尽力而为。
- Eval 重启后需手动“继续跟踪已有任务”，不会自动再次提交。没有返回任务 ID 的不确定请求不能盲目重发，需要先到 Hearth 核实。
- 每轮修复使用独立任务 ID，便于对照原任务与修复结果。一次请求最多初始执行加一次修复。
- 验收记录保存在当前 Eval SQLite 的 `acceptance_jobs` 表中，记录固定要求、任务 ID、反馈、检查项、哈希和时间；不保存完整文件正文。
- 通过代表检查时该文件符合这些要求，不代表之后的文件修改也通过。

## API 与扩展

`GET /api/acceptance/defaults` 返回桌面目录和示例要求；`POST /api/acceptance` 接收 `requestId`（UUID）、`fileName`、`title`、`requiredText`、`maxRepairs`（0 或 1）。重复相同请求 ID 不会创建第二个任务；同一 ID 更改要求会被拒绝。

`GET /api/acceptance` / `GET /api/acceptance/:id` 查看历史和证据；`POST /api/acceptance/:id/resume` / `stop` 继续或停止。接口限本机访问。

`AcceptanceExecutor` 将 `create` / `inspect` / `cancel` / 可选的 `artifact` 下载与交付、文件检查分开。后续接其他 Agent 时实现适配器即可复用本闭环；直接写目标文件的执行器可以省略 `artifact`。当前版本仅提供同机 Hearth native 执行器。

自动化测试使用临时目录和模拟执行器覆盖失败→修复→复测、预算、取消、重启恢复、幂等和路径保护。真实模型验收结果须另外记录，不能用这些测试代替。

## 最小共享记忆闭环

在交付验收页面启用“使用共享记忆与语义评审”，填写项目记忆标识（如 `hearth-eval`），保存项目事实与偏好，再填写本次内容要求。先在“系统 → 模型评委”配置独立模型。未启用此选项时仍使用原有文件规则检查。

本版使用 Eval SQLite 中的本地共享记忆，不连接 Waku，也不会读取其他软件的私人聊天历史。Hearth 通过任务提示词收到固定快照；其他同机工具可以通过下面的 API 读写同一份项目记忆。当前按项目标识精确读取，暂不做向量搜索、自动事实提取或跨设备同步。

流程：保存项目事实 → 按指定版本读取并保存快照 → Hearth 参考快照生成 → 交付与文件检查 → 独立语义评审 → 不通过则按同一快照修复 → 验收记录自动进入共享记忆的 `outcomes`。

- 事实记忆包含版本、来源、更新时间和内容 SHA-256。任务保存完整快照，即使记忆后续更新，执行、修复和评审仍使用旧快照。
- 语义评审检查事实准确性、要求完整性、表达与受众适配；保存模型名、提示词哈希、产物哈希、结论和原文证据。评委引用不存在的原文、评分项缺失、通过结论置信度低于 0.7 或服务失败，均进入“需要处理”，不会降级为通过。模型判断仍有误差。
- 语义评审会向用户配置的模型服务发送固定上下文、本次要求和实际 Markdown 正文。评审单次等待上限 60 秒；超时可以继续跟踪重试，底层请求可能稍后结束，其迟到结果不会改变验收记录。
- `outcomes` 是已结束任务的共享验收记录，引用任务 ID、记忆版本和文件哈希；它不会自动改写项目事实，也不代表文件后来被修改后仍然通过。中断、错误和停止的任务仍可在验收历史中查看。
- 保存记忆和开始任务均校验版本，防止悄悄覆盖其他工具的更新。页面只使用已保存的记忆。

本机 API（沿用本机来源保护）：

```text
GET /api/acceptance/memory/:key
  → { memory: { key, revision, content, sha256, source, updatedAt } | null, outcomes: [...] }
PUT /api/acceptance/memory/:key
  ← { content: "项目事实和偏好", expectedRevision: 0 }
  → 新版本记忆；首次创建用 0，更新用刚读取的 revision
POST /api/acceptance
  ← 原有字段 + memoryKey + memoryRevision + semanticRequirements
```

项目事实最多 1500 字符，内容要求最多 500 字符；两者连同修复反馈受 Hearth 普通任务 4000 字符上限约束。执行器只接收事实快照，不将历史验收结论当成新任务已通过的证据。
